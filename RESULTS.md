## Important limitation: delayed failure response

On this exact Envoy build, upstream extproc denials requesting an immediate 503
and gRPC service outages resulted in a **504 at the five-second route timeout**.
Backend counters stayed unchanged, so the request failed closed. This is not
acceptable evidence of prompt failure handling. The spike records the observed
behavior; it does not establish the root cause. Qualify/fix this on the intended
Envoy version before adopting the design in production.

## Limits of the result

This establishes one bearer-auth implementation serving two traffic paths, not
OAuth acquisition, body signing, retry behavior, SDS, mTLS or Turso replication.
LLM traffic is ordinary chat-completion-shaped HTTP; it does not execute an LLM
provider transformation chain. MCP does execute the pinned real proxy's normal
outbound path, via a minimal launcher and a fake protocol server.

The authd stop/restart test recreates the gRPC service and in-memory database in
one test process, not a separate OS-process crash. The MCP fixture is a separate
process and is not race-instrumented. The race detector covers the auth service,
store and test harness.

A live `lsof` snapshot found no database, WAL or journal file. Combined with SQLite
PRAGMA checks this supports the selected in-memory storage behavior, but it is
not a complete syscall/file-write audit. Swap and core-dump protections are not
qualified. The broader design's full file-activity audit remains outstanding.

No production code, real credentials, cluster or deployment was changed.
